## 速读

想让模型读完一百万个 token（几十本书那么长）时，卡点不在"记不记得住"，而在"看一眼要花多少钱"：标准注意力让每个新 token 都去看全部旧 token，成本随长度平方增长，长到一定程度就贵得跑不动。DeepSeek-V4 的关键动作是把"看什么"和"存什么"分开省钱——先把每 m 个 token 的 KV 缓存合并成 1 条（存的东西变成原来的 1/m），再让每个查询只挑其中最相关的 k 条来看（看的东西也只剩一小撮）。于是同样长度的上下文，算力降到旧版的约四分之一、显存降到约十分之一，而百万 token 内的检索能力依然很强。以后再看到"支持超长上下文"的宣传，我不会只问"窗口多大"，而会先问"它是把每个 token 都认真看了，还是压缩加挑选后近似地看，代价落在哪一档"。

## 它到底在解决什么

具体的卡点是这样一个反差：一个 agent 要跨几十份文档做分析、或做很长的链式推理时，上下文动辄几十万甚至上百万 token。此时模型真正的瓶颈不是"能不能装下"，而是注意力的账算不起——标准（vanilla）注意力里，每生成一个 token，都要和前面所有 token 两两比对一次，总成本随序列长度呈平方增长。论文把这句叫"prohibitive bottleneck"：长度翻十倍，注意力开销翻百倍。

原来人们怎么应对？要么硬扛这份平方成本（窗口越长越烧钱），要么用各种稀疏/线性近似砍掉一部分注意力，但往往在"检索精度"上打折——需要精确回忆某个细节时就丢了。这里缺一个关键区分：省钱可以省在两个不同的地方——省"存下多少"（KV 缓存大小）和省"每次看多少"（每个 query 关注的对象数量）。旧方法常常把这两件事捆在一起,一刀切下去精度就掉。讲到这里，读者会开始期待：能不能在这两处分别、可控地省，而不牺牲精确回忆？

## 它真正看见了什么

一句话的新判断：长上下文的高效，不是"少看几个 token"这一个开关，而是"先把要存的东西压小，再在压小后的东西里稀疏地挑"这两步的组合；两步各自可调，就能把成本和精度分别摆放到想要的位置。

要看懂这个组合，得先补三个承重概念，它们按依赖关系一层套一层。

第一个是**KV 缓存**（存下来供后续查询回看的键值对）。它区分的是"当前要算的 query"和"过去已经算好、被反复回看的历史"。注意力的显存和读取成本，主要压在这份不断变长的历史上。它不是模型参数，而是随对话/文档长度线性膨胀的运行时开销。锚点里的百万 token，膨胀的正是它。

第二个是**压缩**（把每 m 个相邻 token 的 KV 合并成 1 条entry）。这里的"压缩"不是简单取平均池化，而是学出来的加权聚合：先做投影，再按可学习的权重和位置偏置做 Softmax，把 m 条软加权成 1 条（论文式 9–12）。它区分的是"丢信息式的截断"和"保留式的浓缩"——序列长度被压到 1/m，但每条 entry 仍是 m 个原始 token 的加权代表。它直接决定了"存下多少"这一档成本。

第三个是**稀疏挑选**（每个 query 只关注 k 条最相关的 entry），由 DeepSeek Sparse Attention（DSA）配合 **Lightning Indexer** 完成。Indexer 之所以"轻量"，恰恰依赖前一步的压缩：它只在已经压成 1/m 数量的 entry 上打分，query 端还走低秩投影生成，打分只用一个 ReLU 点积加权求和（式 16），再由 top-k 选择器留下最相关的 k 条（式 17）。它区分的是"看全部历史"和"只看被点名的一小撮"——决定了"每次看多少"这一档成本。注意它和压缩是两个独立旋钮：压缩改的是 entry 总数，挑选改的是每个 query 触达的 entry 数。

三个概念接起来，就是论文的两种注意力，以及它们的**混合**方式：

- **CSA（Compressed Sparse Attention，压缩稀疏注意力）**：轻压缩（1/m）+ 稀疏挑 top-k。既省存、又省看，偏"精细/可检索"，适合需要精确回忆细节的场合。
- **HCA（Heavily Compressed Attention，重压缩注意力）**：用远大得多的压缩率 m′（m′ ≫ m）把 KV 压得更狠（1/m′），但保持 dense（每个 query 仍看全部压缩后的 entry）。偏"激进省存 + 全局粗粒度"。
- 混合不是同一层里并行，而是**跨层交替**（interleaved）：有的层用 CSA 精挑，有的层用 HCA 粗看，靠层与层的交替兼顾"精确检索"与"全局覆盖"。

把它接成最小解释模型：

```text
超长上下文(百万token)
  -> 压缩: 每 m 个 token 的 KV 软加权成 1 条 (存下的东西 -> 1/m)
  -> 稀疏挑选: Lightning Indexer 在压缩后的 entry 上打分, 每 query 只取 top-k
  -> 首个可观察变化: 注意力的算力与显存不再随长度平方膨胀
  -> 现象: 同长度下 FLOPs 约降到旧版 27%, KV 缓存约降到 10%, 而百万 token 检索仍强
```

区分一个邻近情况：如果只做压缩、不做稀疏挑选（相当于 HCA 那一路），存是省了，但每个 query 仍要看全部压缩 entry，压得越狠细节丢得越多——所以纯 HCA 适合粗粒度全局，而需要精确回忆时得靠 CSA 的稀疏精挑补上。这正是"两步各自可调"的价值：单靠任一步都会在某一端吃亏。

改变一个条件预测会怎样：把压缩率 m 调得越大（压得越狠），最先观察到的不是崩溃，而是**长距离精确检索的退化**。论文的证据正好落在这条关系上——V4-Pro 在 128K token 以内检索性能高度稳定，超过 128K 后出现可见退化，但到 1M token 仍被评价为"remarkably strong"（较稳地显示：MRCR-1M 上 V4-Pro 得 83.5，超过 Gemini-3.1-Pro 的 76.3，但落后 Claude Opus 4.6 的 92.9）。这说明压缩+稀疏是有代价的近似：它把成本这一端压下去，代价体现在超长距离的精确回忆这一端，而非全面失效。

需要标清分寸的地方：约 27% FLOPs / 10% KV 缓存这组数字是与自家 V3.2 的对比（V4-Flash 更激进，约 10% FLOPs / 7% KV），属于"在这些条件下显示"的工程效率增益，不等于普适定律；而"两个旋钮独立可调带来精度-成本可分配"更多是架构设计推演加上述检索曲线的间接支持，并非直接的消融证明。此外，坊间传的"Anticipatory Routing""SwiGLU Clamping"在原文中并不存在——MoE 侧的实际改动是亲和度从 Sigmoid 换成 Sqrt(Softplus)、免辅助损失的负载均衡、以及初始块改用 Hash routing，别把不存在的术语当卖点。

## 我能带走什么

以后看到"支持 100 万 token 上下文"这类宣传，我先不急着判断"它一定什么都记得住"，而先问三件事：它省的是"存"还是"看"，还是两者分开省？压缩/稀疏的代价落在哪一档——是全局粗糙，还是超长距离的精确检索退化？宣传的效率数字是跟谁比、在什么条件下测的？

一个可复用的判断尺子：把长上下文能力拆成"存多少（KV 缓存）"和"每次看多少（每 query 关注数）"两个独立维度去看，而不是笼统看"窗口多大"。当有人只给窗口长度、不交代这两个维度的代价时，大概率是把"压缩近似地看"包装成了"全部认真地看"。
