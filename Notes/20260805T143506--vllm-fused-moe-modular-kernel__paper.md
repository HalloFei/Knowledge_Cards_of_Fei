# 把 MoE 的算子组合爆炸拆成可拼装的三段

**副标题**: Fused MoE Modular Kernel（vLLM 设计文档）

**日期**: 2026-08-05

**来源**: https://docs.vllm.ai/en/stable/design/fused_moe_modular_kernel/

**作者**: vLLM Project

**发表场所**: vLLM 官方设计文档 / 2026

---

## 速读

一个 MoE 层跑一次要串起很多小算子：量化、把 token 发给对的专家（Dispatch）、两次矩阵乘、激活、把结果收回来（Combine）、按权重加权求和。麻烦在于每一步都有好几种实现，尤其是「怎么在多卡之间发/收 token」这一步（All2All）花样最多。如果让每种 All2All 各自配一整套完整的 MoE 实现，组合数会爆炸，代码到处重复。vLLM 的解法不是发明新算法，而是把这一长串算子切成**三个有明确边界的可替换部件**，让「多卡通信怎么做」和「专家计算怎么做」彼此不知道对方细节，就能自由拼装。以后再看到 MoE 推理慢或想换通信后端，我不会先想「要不要重写整个 kernel」，而先问「是哪一段部件不匹配，能不能只换那一段」。

## 它到底在解决什么

先看一个具体的工程困境。MoE（混合专家）层做一次前向，实际上是一连串算子接力：先把输入量化，再把每个 token 按路由结果**发送**到它选中的专家所在的卡上，专家那边做两次矩阵乘加一个激活，然后把结果**收**回原来的位置，最后按 TopK 权重加权求和。

问题出在「发」和「收」这一步——文档里叫 All2All Dispatch / Combine。它有很多种实现：高吞吐的、低延迟的、不同硬件后端的。而专家计算那一段（矩阵乘、量化格式）本身也有很多变体。老做法是：每来一种新的通信方式，就配一套从头到尾的完整 MoE 实现。于是实现数量约等于「通信方式 × 专家计算方式」，很快就多到没法维护，而且大量代码在重复做同样的事。

旧做法缺的不是某个算法，而是一个**区分**：它没有把「token 在卡间怎么流动」和「专家在本地怎么算」当成两件可以独立更换的事。两者被焊死在一起，所以任何一边变化都要复制整条流水线。

## 它真正看见了什么

新判断用一句话说：只要在流水线的**接缝**处定义好稳定的数据格式和调用约定，就能把一条长流水线切成几段独立开发、独立测试、任意拼装的部件，组合爆炸就被摊平成「几个部件各自的少数实现」。

要理解这个切法，需要几个承重概念，按它们互相依赖的顺序展开。

**第一个是「激活的两种格式」**，因为整条流水线的形状由它决定。token 从 Dispatch 出来后长什么样，取决于用了哪种 All2All：
- *Contiguous（连续/标准）*：所有 token 挤成一个 `(M, K)` 的连续张量，另配一份 TopK 的 id 和权重。
- *Batched（分批）*：按专家分组，张量形状是 `(专家数, 每专家最多token数, K)`，还附一个 `expert_num_tokens` 说明每个专家实际收到几个有效 token（其余是占位的无效槽）。

这个区分为什么承重？因为它直接决定后续要不要做 Permute/Unpermute（把同一专家的 token 排到一起、算完再排回去）——Batched 本身已经按专家分好组，Non-Batched 则需要显式排列。文档明说：两种情况唯一的算子差别就在 Permute/Unpermute，其余算子都一样。

**第二个是把流水线切成的三段部件**，这是文档的核心结构：

- *FusedMoEPrepareAndFinalizeModular*（前处理与收尾）：管两头。`prepare` 做量化 + All2All Dispatch（发出去），`finalize` 做 All2All Combine（收回来）。它背后通常绑定一种具体的 All2All 通信 kernel。
- *FusedMoEExpertsModular*（专家计算）：管中间。它的 `apply` 干最重的活——Permute、乘 W1、激活相乘、量化、乘 W2、Unpermute。
- *TopKWeightAndReduce*（加权求和）：管「按 TopK 权重加权再求和」这一小步。

**第三个概念是 TopKWeightAndReduce 为什么要单独抽出来**，它是这套设计里最能体现「接缝约定」思想的地方。加权求和这一步，逻辑上夹在 Unpermute 之后、Combine 之前——也就是正好跨在「专家计算」和「收尾」两段的边界上。有的专家实现顺手就把它做了（更高效），有的则希望留给收尾阶段做。如果写死在某一段，另一种实现就没法复用。

vLLM 的解法是：让专家部件通过 `finalize_weight_and_reduce_impl()` **返回一个对象**，声明「这一步我做了没有」——做了就返回 `TopKWeightAndReduceNoOp`（收尾阶段别再做），没做就返回具体的 reduce 实现（请收尾阶段照此执行）。这样两段都不用知道对方的内部选择，只靠这个返回值协商。这就是「接缝约定」的具体样子：不是共享代码，而是共享一个明确的交接契约。

把三段接成最小模型：

```text
输入激活
  |
  v
[Prepare]  量化 + All2All Dispatch  -->决定激活格式(Contiguous/Batched)
  |
  v
[Experts.apply]  (Permute) 乘W1 -> 激活 -> 量化 -> 乘W2 -> (Unpermute)
  |              并通过 finalize_weight_and_reduce_impl() 声明是否已做加权求和
  v
[Finalize]  按声明决定是否做 TopK 加权求和 + All2All Combine
  |
  v
输出
```

`FusedMoEModularKernel` 本身只是个**装配壳子**：构造时塞进一个 prepare_finalize 和一个 experts 对象，`forward` 里依次调用 `prepare -> workspace_shapes -> apply -> finalize`，中间还统一预分配 workspace 缓冲区（避免每个算子各自开内存）。它不含任何算法，只负责按约定把两段接起来。

**换一个条件看模型的预测力**：如果 Dispatch 换成 Batched 变体（比如低延迟的 DeepEP LL），首先变的是激活张量形状变成 `(专家数, 最多token数, K)` 且带无效槽，于是 Experts 段内部的 Permute 逻辑随之不同——但 Prepare 段和 Finalize 段的调用契约不变。这正是解耦的收益：换通信后端不牵动专家实现。反过来，一个**邻近但不同**的情况是：某个专家实现选择自己做加权求和，那么它返回 `NoOp`，Finalize 段就跳过 reduce——外部装配代码一行都不用改，结果依然正确。

证据方面要说清分寸：这是一份**设计文档**，不是实验报告。它没有给出「解耦后快了多少」的性能数字。它证明的是**可维护性和可组合性**——文档明确说这么做「让组合变得可管理、避免代码重复、让 All2All 与专家实现能独立开发和测试」，并配了单元测试遍历所有部件组合来验证兼容性。所以它最多说明「这套结构让扩展新通信/新量化格式更省事、更不易出错」，尚未说明（也没打算说明）它比某个手写融合 kernel 更快。把它当成一把**组织复杂度的尺子**，而不是一个性能优化结论。

## 我能带走什么

以后遇到「一条长流水线，每一环都有多种实现，组合起来要维护的版本爆炸」这种工程困境，我先不急着为每种组合各写一套完整实现，而先问：**这条流水线的接缝在哪里？能不能在接缝处定一个稳定的数据格式 + 交接契约，让上下游互相不知道对方细节？**

这个思路的两个真正相关的用法：一是识别「藏在边界上的可选步骤」（像这里的加权求和），用「返回一个声明对象」让两侧协商，而不是把选择写死在某一侧；二是判断一个抽象是否值得做——如果拆分只是换个名字包装，没有真正切断上下游的相互依赖，那它就是伪模块化，不会带来独立开发和测试的收益。
