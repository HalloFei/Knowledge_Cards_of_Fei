# 提示词是参数，跑通的轨迹是教材

**副标题**: DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines

**日期**: 2026-10-23

**来源**: https://arxiv.org/abs/2310.03714

**作者**: Omar Khattab, Arnav Singhvi, Paridhi Maheshwari, Zhiyuan Zhang, Keshav Santhanam, Sri Vardhamanan, Saiful Haq, Ashutosh Sharma, Thomas T. Joshi, Hanna Moazam, Heather Miller, Matei Zaharia, Christopher Potts

**发表场所**: arXiv preprint (2023)

---

## 速读

一条两跳的问答链，中间那一步要"看着三段检索结果，写出下一句该查什么"。这一步没有现成提示词可抄——它只存在于你刚画出来的这张图里。DSPy 的判断是：这一步"怎么问"不是知识，是参数；而能教这个参数的数据，不在数据集里，在这条流水线自己的运行记录里。跑几遍，把终点过关的那几条轨迹录下来，每一步就都有了自己真实见过的输入输出对，可以拿去当示范。于是"写提示词"变成"编译"：声明每步吃什么吐什么，让编译器用轨迹去填"怎么问"，换个模型重编一次就行。带走一句：以后某一步不听话，先别改措辞，先问"我有没有它自己跑通的那一次"；如果喂了自己的轨迹还是不动，问题就不在措辞，在那一步根本没拿到它需要的信息。

## 它到底在解决什么

你搭了一条两跳的问答链：先检索一次；看一眼结果，写出更好的检索词；再检索一次；最后拿着两轮结果作答。搭完，你盯着中间那一步发呆——它的提示词该写什么？

抄不到。这个问题（"给定这三段维基摘要和原问题，下一个该查什么"）没有论文、没有模板库、没有 Stack Overflow，因为它不是一个任务，是你这张图里长出来的一个中间步骤。于是常见的三种处理是：写一句"请生成一个好的检索词"；从别处抄一段看起来相近的提示；或者干脆放弃，退回一步到位的问答——也就是把图的边全拆了，回去手工调那一句。

框架给过答案：预打包的链和模板。但它覆盖的是已经被无数人写过的那一层，你图里真正卡住的那一步，恰好是没人写过的那一层。这就是这篇要动的地方。

更深一层的问题是：即使你写出一句漂亮的提示词，它也只对某一个模型、某一类输入有效。换个模型，你无法预知它还灵不灵；加一步，前面那句可能要重写。作者把这个状态比作手工调权重——你在用人的手感，去填一个本该由数据决定的位置。他们翻了 LangChain 的代码库，一千字符以上的字符串有 50 个，基本都是提示词。

如果"怎么问"真的可以由数据决定，那它得先能被当成一个空位。这篇的第一个动作，就是把空位刻出来。

## 它真正看见了什么

一句人话：**一条流水线里，每个模块该说什么，取决于它收到了什么；而它真正会收到什么，只有跑起来才知道。**

刻空位的办法是签名（signature）：只说这一步吃什么、吐什么，不说怎么问。`question -> answer` 一行就是一个完整程序。字段名本身带着语义，DSPy 会把 `english_document -> french_translation` 读成翻译，把 `context, question -> search_query` 读成出检索词。同一个 RAG 骨架，签名从 `-> answer` 换成 `-> search_query`，它就从答题变成了出检索词：骨架没动，角色变了。这验证了"要做什么"和"怎么说"确实是两件事，而且前者足以把后者约束到可以被优化的程度。

技巧也被改造成了形状，而不是句子。ChainOfThought 的实现只有几行：在签名里插一个中间输出字段（比如 rationale），再调一次 Predict。它没有把"让我们一步步思考"写死成流程，那句话只是一个字段前缀；真正的结构是"先产出一个中间字段，再产出答案"。这个区别很要紧：一旦技巧是形状，它就能跟着签名走到任何任务上。同一个 ChainOfThought，这一头套在 GSM8K 的答题上，那一头套在 HotPotQA 的"写检索词"上，都成立。而"给定三段摘要和原问题，下一条查什么"正好是没人写过的步骤——技巧能搬过去，是因为它搬的是形状。

接下来的问题是：这个空位填什么？数据集的答案是填不了的。数据集给的是任务样本（题加答案），而模块需要的是经历——它这一次实际收到了什么、实际吐出了什么。这两者差得很远：那个出检索词的模块，真实输入里躺着这一轮检索回来的三段摘要，有相关的、有跑偏的、有只对上一跳有用的；换成一条干净的数据集样本，这些噪声就全没了。

所以编译时，程序把每一步的输入输出都录下来。跑完看终点：终点过了 metric（比如最终答案的 EM），这整条轨迹才算数，然后被切成一段一段，每一段发给对应模块当示范；没过就整条丢掉。这就是倒灌：**一个最终的判断，替一条链上每一步都发了一次标签**，不需要人给中间步骤标注。也因此，换一条流水线不用重新标注数据，重编一次就行——程序里只有输入和最终答案，中间那些标签是跑出来的。

看论文附录里那条真被编译出来的示范：context 是三段真实的 Twilight 小说条目，question 是另一道题，然后才是"这题该查什么"。这段转录没有人写得出，它记录的是一个具体模型、一个具体检索器、一次具体运行。这解释了一个表面上的怪现象：作者拿人写的推理链示范，和系统自己 bootstrap 出来的示范做对照——强模型上两者打平（GPT-3.5：78.6 对 80.3），弱模型上自己搜出来的反而高出一大截（llama2：43.3 对 34.3）。人写的那条是"正确答案长什么样"，模型自己那条是"这个模型做对时长什么样"，后者更可模仿。示范的价值不全在它多正确，也在它从哪来。

于是 metric 从"评分标准"变成了"教材的编者"。它松在哪，系统就往哪里长，因为松的地方最容易产出过关的轨迹。GSM8K 只从输出里抽最后一个数字，所以"在 answer 字段里先把演算写一遍"完全合法。那个一步式的 vanilla 程序编译两轮之后，自动长出来的提示词就是这样：答案字段里塞着一整段推导。人不会这么写，因为人在写指令；编译器在录成功行为。GPT-3.5 上这个一步式程序从 25 涨到 62（test），涨的不是模块，是示范教会了它"在这个字段里可以先算"。

到此为止，"怎么问"已经是一个可以被搜索的参数：候选是一堆示范集合，选择靠验证集分数（随机搜索、Optuna），或者干脆把轨迹拿去微调一个小模型。但这只是参数优化，图本身是固定的——所以天花板是图定的。

同一个编译器，HotPotQA 上，CoT_RAG（从原问题直接检索一次就作答）从 36 抬到 42（dev，GPT-3.5）；multihop（用第一跳的上下文生成第二跳的检索词）从 37 抬到 49。差的不是优化力度，是图里那条"第二跳的检索词由第一跳看到的东西决定"的边。CoT_RAG 没有这条边，编译器再拼也只能让它在"一次检索够不够"的范围里变好。涨不动是结构问题，不是示范问题。

再往上还有两级。第一级是换老师：把已经编译好的程序当 teacher，用它重新生成轨迹。第一轮的轨迹受限于当时那个笨程序，第二轮的老师已经会做了，轨迹更接近"做对时的样子"。ReAct 在 llama2 上从 24.7 走到 40.0（dev）靠的就是这一跳——不是多训了几遍，是换了个人教。第二级是改图：并行跑多份再按多数投票合并。这一步不动参数，动结构，GSM8K 上 CoT 加集成到 88（dev），全表最高。优化到一个程度之后，收益最大的动作往往是改结构，而不是继续挑示范。

整条回路长这样：

```text
 程序   输入 ─> [写检索词] ─> 检索 ─> [作答] ─> 答案
                    │           │         │
                    └───────────┴─────────┘
                     每一步的输入和输出都被录成轨迹
                              │
                        终点过了 metric 吗
                        ├─ 没   ─> 整条丢掉
                        └─ 过了 ─> 切成一段段，发给
                                   每个模块当示范
                                        │
                                        v
                        重编一轮：老师是上一轮的自己
```

这个模型可以被检验。把同一个编译器放到两条相邻的流水线上：如果差别只在示范，编译后应当同向涨；如果其中一条根本缺一条边，编译后应当卡住——HotPotQA 上的 CoT_RAG 和 multihop 正是后者，这反过来支持"天花板由图定"。再改一个条件：把 metric 收紧，要求 answer 字段只出现一个数。那么"字段里先演算"那条轨迹在终点就过不了，活不下来，vanilla 的增益会大幅缩水，退回接近零样本的水平。方向是确定的：metric 松一寸，系统就往那一寸里长一尺。

边界得说清楚。这最多说明：在两个任务（小学数学、多跳问答）、两种模型、一个检索器上，用 200 条训练输入和分钟级到十几分钟的编译，能把手写提示词的效果追平甚至超过——弱模型上超得明显，强模型上只是追平。它还没有说明：这套东西能自己发现图的结构（这一版里只有集成算改结构，自动回溯被留在了未来工作里）；也不说明"自我改进"是持续学习，它是在几百次调用里做搜索，跑完就停。

那个 770M 的 T5 最容易误读：编译后在 dev 上 39.3 EM，前提是两个 llama2 集成当老师、800 条无标注问题当原料。它证明的是"小模型可以被大模型跑出来的轨迹教会"，不是"小模型自己会推理"。作者与已发表数字的对照也是非正式的——测试子集和评测口径都不一样，不能当排行榜读。

## 我能带走什么

以后看到流程里某一步不听话，先不问"这句话怎么改"，先问"我有没有它自己跑通的那一次"：有，就把那一次的输入输出原样录下来当示范；没有，就去造一次——跑十遍，留下过关的那几条。

如果喂了自己的轨迹还是不动，别再改措辞了。那多半意味着这一步根本没拿到它需要的信息，问题在图，不在句子。顺带，动手之前先看一眼 metric 松在哪：你会得到一个专门利用那处松动、而且确实能过关的系统。
