一枚 token 进卡之后发生了什么

LLM 推理中的 GPU 参与方式 · 概念图解
companion note: 20260818T115251--gpu-in-llm-inference__concept.md · 前置: gpu-memory-hierarchy.html(内存金字塔) · 2026-08-18

0 · 一句话总览

GPU 根本不认识 Transformer。它每一步只是被推理框架(vLLM 之类)喂进一小段数据和一个 kernel(一段在 SM 上跑的函数);而 LLM 推理的特殊性在于:权重几十 GB 常驻 HBM, 每生成一个 token 都要把它们完整读一遍,却只做很少的计算。

于是推理天然切成两种负载:prefill(并行处理整段 prompt,大矩阵乘,卡算力) 和 decode(每步只算一个新 token,矩阵退化为向量,卡显存带宽)。

1 · GPU 只认识 kernel:一次前向的 kernel 串

框架在 CPU 上把模型各层算子翻译成一串 CUDA kernel,依次发射(launch)到 stream 上异步执行。 GPU 收到的从来不是"跑一个 Transformer",而是"跑这个 GEMM""跑那个 attention"——每次一小段。

token ids→ embedding 查表→ × L 层: QKV投影→ attention→ 输出投影→ MLP ×2→ lm_head(词表×维度)→ 采样→ 新 token

量级差是关键:权重(几十 GB)常驻 HBM; 激活值/logits(MB 级)只在 HBM 短暂停留。一次前向 = SM 阵列轮流把每份权重从 HBM 经 L2 读进来, 乘完就丢、换下一份。每生成一个 token,这套搬运完整走一遍。

2 · prefill vs decode:同一模型,两种负载

prefill(预填充)compute-bound

一口气并行处理整段 prompt 的 N 个 token

  • GEMM 形状:大矩阵 × 大矩阵,SM 吃得饱
  • 计算量随 N 线性涨,权重只读一遍
  • 读带宽被 N 份计算摊薄 → 瓶颈在算力
  • 决定了 TTFT(首 token 延迟)

decode(解码)memory-bound

每步只算 1 个新 token,自回归循环

  • GEMM 退化为矩阵 × 向量(GEMV)
  • 还是读全部权重,却只做 1/N 的计算
  • 算力利用率 <1%,都在等 HBM 流量
  • 决定了 TPOT(每 token 延迟)

3 · 一步 decode 的时间账:为什么卡的是带宽

尺子是算术强度:每读写 1 byte 数据要做多少 FLOP;瓶颈 = max(搬运时间, 计算时间)。 以 7B 模型 FP16 × A100 为例(batch=1):

搬权重 14GB / 2TB/s
~7 ms(每步下限)
计算 14GFLOP / 312TF
~0.05 ms(算力只用 <1%)

GPU 几百 TFLOPS 的算力在 decode 时大部分空转, 晶体管都在等数据从 HBM 流过——这就是内存金字塔"片上快而小、片下大而慢"的张力在推理上的显形。

4 · batch 杠杆:让每次读带宽物尽其用

decode 拼 batch:B 个请求共享同一次权重读取(HBM 流量几乎不变),计算量翻 B 倍 → 算术强度被抬起来,逐步滑向算力受限。vLLM 的 continuous batching 就是每步动态插拔请求、把 B 维持到最大。

B=1
读权重 7ms,算 1 份 → 带宽浪费
B=16
读权重 ~7ms,算 16 份 → 接近回本
B=64+
瓶颈翻转到算力侧 → GPU 喂饱

另一头的限制:KV cache 随序列线性膨胀, batch 上限常常不是算力,而是"KV cache 塞不下了"——PagedAttention 分页正是在 HBM 这一层内部省容量。

5 · vLLM 一步 decode 的完整循环(CPU ↔ GPU)

CPU · vLLM 调度器

  • 组 batch,步间换入/换出请求
  • 查 KV cache block 表
  • 发射 kernel 串(prefill 逐个发)
  • decode 走 CUDA Graph 一次重放整图
  • 把新 token 塞回下一轮 batch
⇄
PCIe
kernel
+token id

GPU · 被动执行

HBM:权重(常驻,几十GB) + KV cache(随序列膨胀) + 本步 token ids(几字节)
GEMVattention(读KV)MLP采样

GPU 只做三件事:收 kernel → 按塔搬运数据 → 交回 logits。什么时候收、收多大批,全由 CPU 决定。

6 · 四环定位:任何推理优化都挂在这条流水线上

a. 省 HBM 容量 让大块头更小

  • 权重量化(14GB→更小)
  • PagedAttention:KV 分页不浪费

b. 省带宽流量 让每次读更值

  • continuous batching 抬算术强度
  • prefix cache 复用已算好的 KV

c. 省跨层搬运 HBM↔片上 SRAM

  • FlashAttention 分块留在片上反复用
  • 算子融合:多个 kernel 并成一个

d. 省 GPU 外空转 launch / 等待

  • CUDA Graph 压 launch 次数
  • 调度与计算重叠、prefill/decode 并行

带走:看到任何 LLM 推理系统优化(vLLM / SGLang / TensorRT-LLM…), 先不记技巧,先问它作用在这四环中的哪一环。识别信号:听它反复念叨的是"容量/占用"、"带宽/复用"、 "搬运/融合",还是"launch/调度"。四环加起来,就是 GPU 参与 LLM 推理的全部戏份。
