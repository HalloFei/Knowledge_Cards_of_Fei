## 📖 Definition

BM25 is a bag-of-words ranking function derived from the probabilistic relevance framework (Robertson & Sparck Jones, 1970s; the Okapi system at City University London, TREC 1990s; consolidated in Robertson & Zaragoza, 2009). It is not a trained model: nothing is fitted to data, only three constants are set by hand. Given a query q and a document d, it sums per-term evidence:

```
score(q, d) = SUM over t in q of  IDF(t) * [ tf(t,d) * (k1 + 1) ]
                                   / [ tf(t,d) + k1 * (1 - b + b * |d| / avgdl) ]

IDF(t) = ln( 1 + (N - df(t) + 0.5) / (df(t) + 0.5) )
```

Each factor does exactly one job:

- `tf(t,d)` - raw occurrences; the only positive evidence.
- `k1` (term-frequency saturation) - the denominator makes extra occurrences return less and less. The 20th occurrence of a word adds almost nothing over the 5th, so keyword stuffing cannot buy score.
- `b` (length normalization) - `|d| / avgdl` penalizes documents that are long only because they contain many unrelated words.
- `IDF(t)` - rare terms carry more evidence than ubiquitous ones. Matching `NullPointerException` says more about relevance than matching `the`.

Defaults: `k1 = 1.2`, `b = 0.75` (Lucene `BM25Similarity`, Elasticsearch). `b = 0` disables length normalization; `b = 1` applies it fully. `k1 -> 0` degenerates into binary "term is present" matching.

## 🧮 Hyperparameters

| Parameter | Default | Effect | When to change |
|---|---|---|---|
| `k1` | 1.2 | How fast term frequency saturates; higher = repeated terms keep paying off | Long queries / long docs: 1.2-2.0. Very short, uniform entries: 0.8-1.0 |
| `b` | 0.75 | Strength of document-length penalty | Memories of similar short length: 0.3-0.5, otherwise the length term is pure noise. Mixed long docs: keep 0.75 |
| analyzer | whitespace words | What counts as a token; dominates real-world quality | CJK text: segmentation (jieba) or character bigrams. Code identifiers: split camelCase / snake_case, keep the raw token too |
| `delta` (BM25+) | 0 | Constant lower bound added per matched term | When long documents are over-penalized |

## 🧠 Why it shows up in "BM25 memory"

"BM25 memory" is not a formal term. It is shorthand for: a memory store whose recall lane is BM25. Each memory entry (a user preference, a past episode, a fact) is treated as a document, the query is the current turn, and the top-k entries are pulled back into the context window.

Why this combination is attractive:

- Exact-token recall. Memories are full of identifiers that embeddings smear: order numbers, error codes, file paths, people's names, version strings. BM25 hits them literally.
- No embedding call. Zero API cost, sub-millisecond-ish latency, works offline, and the index can be updated incrementally as memories are written - unlike a vector store that needs an embedding per write.
- Explainable. You can decompose the score into `IDF(t) * tf-component` per term and say why a memory was recalled.
- Robust out of the box. No training, no domain adaptation, no cold start.

The price: pure lexical matching fails on paraphrase and synonyms ("car" vs "automobile", "cancel my order" vs "I want a refund"). Production memory systems therefore run a hybrid: BM25 recall + dense recall, fused by weighted score or Reciprocal Rank Fusion, then re-weighted by recency and importance - the relevance term is only one of three in Generative Agents' memory scoring (`recency * importance * relevance`).

Concrete systems that do this: Zep/Graphiti combines cosine similarity, Okapi BM25 full-text search and graph traversal; Mem0's v3 pipeline ships hybrid search; LangChain offers `BM25Retriever`; SQLite FTS5 exposes a built-in `bm25()` function, which makes a local memory index a few lines of SQL.

## 🧪 Engineering notes

- **CJK tokenization first.** BM25 lives or dies on the analyzer. Chinese has no spaces; without segmentation an entire sentence becomes one token and the score collapses. Either segment (jieba + custom dictionary for product names) or index character bigrams.
- **Small corpora break IDF.** With N in the hundreds, `df` is noisy and the unsmoothed IDF can go negative (any term appearing in more than half the collection). Use the `ln(1 + ...)` variant above, which stays non-negative.
- **Short documents shift the tuning.** Memories are 10-30 tokens, so `avgdl` is tiny and `b` barely discriminates; drop `b` and lower `k1` before blaming the algorithm.
- **Fusion without calibration.** `RRF(d) = SUM over retrievers 1 / (k + rank(d))`, `k = 60` - rank-based, so no score normalization is needed. Min-max normalized weighted sums work too, but are sensitive to outlier scores.
- **Index maintenance.** Inverted index with postings lists; deletes via tombstones or rebuild. For a personal memory store, FTS5 + triggers is usually enough.

## 🔬 Research (4 entries)

- `[2009] The Probabilistic Relevance Framework: BM25 and Beyond` (Robertson & Zaragoza) - the canonical derivation, the family of variants, and a candid discussion of parameter sensitivity. Search keywords: probabilistic relevance framework BM25.
- `[2011] Lower-Bounding Term Frequency Normalization (BM25+)` (Lv & Zhai) - adds a constant per matched term so that long documents are not over-penalized; the practical fix when `b` tuning stalls. Search keywords: BM25+ lower bounding term frequency.
- `[2021] SPLADE` - learned sparse retrieval: keeps the inverted-index efficiency and exact-term behaviour of BM25 while adding semantic expansion and learned term weights. The closest successor in the sparse family. Search keywords: SPLADE learned sparse retrieval.
- `[2009] Reciprocal Rank Fusion` (Cormack, Clarke & Buettcher) - rank-based fusion with `k = 60`; the default glue for BM25 + dense hybrids. Search keywords: reciprocal rank fusion hybrid retrieval.

## 🔗 Related Concepts (5)

- **IR (Information Retrieval)** - parent discipline: BM25 is one concrete ranking function inside IR, the retrieval half of RAG.
- **TF-IDF** - predecessor: same intuition, but TF is unbounded and there is no length normalization, so long documents dominate. BM25 saturates and normalizes.
- **Dense Retrieval** - complementary: semantic recall for paraphrase; BM25 covers exact tokens and out-of-domain terms. Hybrid beats either alone.
- **Reciprocal Rank Fusion (RRF)** - fusion layer: merges BM25 and dense ranked lists without score calibration.
- **Agent Memory** - application: the store where "BM25 memory" appears; retrieval there is time-aware, not relevance-only.

## ⚖️ Pros and Cons

- **Pros:** (1) No training, no GPU, no embedding API - works offline and on new domains immediately. (2) Exact lexical match for identifiers, codes and names that dense retrieval fumbles. (3) Fully interpretable per-term score decomposition. (4) Cheap index updates on write; well-supported everywhere (Lucene, Elasticsearch, OpenSearch, Tantivy, FTS5, Meilisearch). (5) Strong, stable baseline that is hard to beat on keyword-heavy queries.

- **Cons:** (1) Vocabulary mismatch - synonyms, paraphrase, cross-lingual queries all fail without expansion. (2) Quality is dominated by the analyzer; Chinese/Japanese need segmentation and domain dictionaries. (3) IDF is unstable on small collections; term statistics drift as the corpus grows. (4) Ignores word order, negation and semantics ("not refundable" scores the same as "refundable" on `refund`) - needs phrase/proximity handling or a dense companion. (5) Short, uniform-length memory entries require re-tuning `k1`/`b` that generic defaults do not cover.

## 📌 Takeaway

BM25 is the cheapest reliable relevance signal you can put in front of a corpus - and the reason "hybrid" is the default architecture for both RAG and agent memory. Treat "BM25 memory" as "a BM25 recall lane over memory entries", not as a named algorithm.
