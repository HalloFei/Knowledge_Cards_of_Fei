# 缓存的浪费在层数，不在长度

**副标题**: You Only Cache Once: Decoder-Decoder Architectures for Language Models（YOCO：自解码器只算一次全局 KV，交叉解码器共享它——把"每层独立缓存"改成"全局一份"）

**日期**: 2026-10-21

**来源**: https://arxiv.org/abs/2405.05254

**作者**: Yutao Sun, Li Dong, Yi Zhu, Shaohan Huang, Wenhui Wang, Shuming Ma, Quanlu Zhang, Jianyong Wang, Furu Wei（Microsoft Research / 清华大学）

**发表场所**: arXiv 预印本（arXiv:2405.05254v2，2024-05）

---

## 速读

长上下文推理时，显存不是被权重吃掉的，是被 KV cache 吃掉的：65B 模型、512K token，缓存就要约 86 GB，比模型本身还大，预填要 180 秒。主流优化——GQA、量化、驱逐、稀疏——都在压缩"每一份缓存"的大小，但没人问：同样一段历史，为什么要按层数存 L 份？YOCO 把模型劈成两半：前一半用线性注意力把整段上下文编码成**一份**全局 KV，后一半所有层共享这一份。缓存从 O(L·N) 掉到 O(N)。1M 上下文总显存 12.4 GB（Transformer 的 1/9.38），512K 预填从 180 秒降到 6 秒以内，语言建模分数没掉。以后看长上下文方案，我先问它减的是"每份的大小"还是"份数"。

## 它到底在解决什么

一个具体的数字：65B 的模型，配上 GQA 和 8-bit KV 量化，512K token 的 KV cache 大约 86 GB——比 65B 权重（130 GB 的 fp16，量化后更小）之外还要多出这么一大块。预填这一段要 180 秒。

显存是硬墙，撞上去的后果很直接：batch size 被压到 1，吞吐起不来；上下文再长一点，消费级显卡根本放不下。

行业原来的做法是做减法，减在"每一份缓存"上：MQA/GQA 减少 KV 头数，量化降低每份的位宽，驱逐和稀疏只保留重要的 token，分页减少碎片。这些都有效，而且可以叠加。

但它们共同绕过了一个乘数：**层数 L**。decoder-only 的每一层都要各自算 K/V、各自缓存，因为每层参数不同、表示不同。这件事太自然了，自然到没人把它当成浪费——它就是架构的定义。

这篇论文换了个问法：如果所有层最终都在看同一段历史，为什么每层要各存一份？

在回答问题之前，得先看清它到底改了什么。

## 它真正看见了什么

一句话：KV cache 的主要冗余不是"每份太大"，而是"存了 L 份"；把所有权从每层改成全局，比把每份压小更彻底。

**结构是怎么变的。** YOCO 是 decoder-decoder：前 L/2 层是自解码器，后 L/2 层是交叉解码器。

- **自解码器**用高效注意力（论文试了门控保留 gRet 和固定窗口滑窗两种）把整段输入编码一遍，输出一份全局的 K̂、V̂。它自己的推理缓存是 O(1)——滑窗只看窗口内，gRet 是循环状态。
- **交叉解码器**的每一层只带自己的 Q，去 cross-attend 这份共享的 K̂、V̂，不再各自存 K/V。

于是缓存量从"每层 N 个"变成"一份 N 个 + 每层一个常数"，也就是 O(N)。层数不再是乘数，只是加数。

**第二个收益是白捡的：预填可以提前退出。** 生成阶段只需要这份全局缓存和最后一个 token，根本用不到交叉解码器的中间激活，所以预填时算完自解码器就能停。输出完全不变，成本至少减半；再叠加自解码器的线性复杂度，512K 的预填从 180 秒掉到 6 秒以内。

```text
输入 x1 … xN
   │
   ▼
自解码器（L/2 层，gRet 或固定窗口滑窗）
   │  只产出这一份：K̂, V̂   ← 全局唯一被缓存的 KV
   ▼
交叉解码器（L/2 层，全局 cross-attention）
   │  每层自带 Q，共享同一份 K̂、V̂
   ▼
输出 logits
```

**回到锚点。** 1M 上下文，总推理显存 12.4 GB，是 Transformer 的 1/9.38；每 token 的缓存省 24× 到 80×，而且**模型越大省得越多**（1.2B 省 24×，65B 省 80×）——因为省的正是 L 这个因子。

**一个邻近情况能测出区别。** GQA 也省缓存，但它省的是 KV 头数，L 还在。论文给了个对照：1 GB 显存，YOCO 能服务 128K token，65B + GQA 的 Transformer 只能服务 1.6K。差了 80 倍——这不是"压缩率"的差别，是"层数因子有没有被消掉"的差别。所以两者不是替代关系，是正交的，可以叠加。

**再变一个条件。** 把自解码器换成全局注意力（不再 O(1)），它自己的缓存立刻变成 O(L/2 · N)，"只存一次"的收益当场吐回去一半以上。所以"自解码器必须是 O(1) 缓存"不是实现偏好，是这个架构成立的前提；换一个更准但更贵的高效注意力，就是在拿结构收益换质量。

**证据贴着主张。** 3B 模型、1.6T token，评测平均 0.636，同规模的开源 Transformer 基线在 0.61–0.62 一线，1T 和 1.6T 两个 checkpoint 趋势一致；160M 到 13B 的 scaling 曲线基本贴合，且略优；1M 长度的 needle 检索，N=1/2/4/8 的命中率 0.98/0.98/0.84/0.56，与专门做长文的 LWM-1M（1.00/0.90/0.76/0.62）在同一量级。吞吐：512K 下从 4.5 token/s 到 43.1 token/s。

**边界要说清。** 对比基线是他们自己同配方训练的 Transformer，主要落在 3B；13B 只出现在 scaling 曲线里，没有公开评测。86 GB、1.6K token 这类数字带估算（GQA + 8-bit），不是实测。长文评测用 needle-in-a-haystack，考的是"能不能捞出来"，不是"能不能在长文上推理"。最关键的一个空白：论文没有消融"如果留两份缓存会怎样"——"一份到底够不够"这个问题，只给了端到端结果，没给中间诊断。所有层的表达能力被压进同一份表示，损失在哪、有多大，目前不知道。另外吞吐数字依赖他们自己写的 Triton kernel 和 H100，换生产栈会变。

## 我能带走什么

一条判断规则：以后评估一个长上下文方案，先问它减的是**每份的大小**还是**份数**。前者有下限——精度、头数、窗口，压到一定程度就伤质量；后者直接乘在层数上，模型越深越划算。

两个真正相关的用法。看架构提案时：只做 attention 内部的稀疏、量化、驱逐，L 这个因子没动，收益会随模型变深而稀释；改了"谁拥有缓存"，收益会随模型变深而放大。做部署预算时：先看 O(L·N·D) 里哪一项你能动——上下文长度常常是产品需求，砍不得；层数是模型设计，可以改。所以后者才是结构性的杠杆。

这篇论文最耐用的地方，可能不是 YOCO 这个具体架构，而是它提出的那个问法：**缓存该归谁所有。** 一旦问出来，压缩、索引、预缓存这些后续动作才有地方挂。
