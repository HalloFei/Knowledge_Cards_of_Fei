# 显存不是算不动,是被留白浪费掉了

**副标题**: Efficient Memory Management for Large Language Model Serving with PagedAttention

**日期**: 2026-08-13

**来源**: https://arxiv.org/abs/2309.06180

**作者**: Woosuk Kwon, Zhuohan Li, Siyuan Zhuang, Ying Sheng, Lianmin Zheng, Cody Hao Yu, Joseph E. Gonzalez, Hao Zhang, Ion Stoica

**发表场所**: SOSP 2023

---

## 速读

一张 A100 上,模型权重占 65% 显存,剩下的几乎全被 KV cache 吃掉——而 KV cache 才是决定能同时塞多少请求(batch size)的那块地。诡异之处在于:实测里这块地真正装了有效数据的只有 20%~38%,其余全是"留白"。留白不是因为模型算不动,而是因为旧系统被"张量必须存在连续内存"这条工程惯例逼着,为每个请求按**最大可能长度**预留一整块连续显存;请求实际长度远短于上限,预留出去的空间又不能借给别人,于是显存在"没满却也没法用"的状态里空转。这篇论文把操作系统里"虚拟内存+分页"那套搬进注意力计算:KV cache 切成固定大小的小块,块之间不必连续,用一张映射表把"逻辑块"翻译成散落各处的"物理块"。有效显存利用率直接逼近满格,同一批能塞进去的请求随之翻倍,吞吐提升 2-4 倍。以后我再看到"显存不够、batch 上不去",第一反应不该是"该换更大的卡",而该先问:是真的装满了,还是被预留和碎片浪费了?

## 它到底在解决什么

先看一个刺眼的数字:同样的显卡、同样的模型,旧系统里 KV cache 这块显存,平均只有 20%~38% 真正存着有用的数据(论文 Fig. 2)。剩下六到八成去哪了?

要理解这个浪费,先得看清 **KV cache** 是什么、为什么它会动。大模型逐字生成,每生成一个新字,都要回看前面所有字。为了不每次重算,系统把前面每个 token 算出的 key/value 向量缓存起来,这就是 KV cache。它有两个和普通张量不一样的脾气:一是**边生成边变长**,生成到哪才知道占多少;二是**生成多长事先不知道**,可能几十个 token 就结束,也可能顶到 2048。

旧系统卡在一条深植于深度学习框架的工程惯例上:**张量必须存在一段连续内存里**。为了满足这条,它只能在请求一进来时,就按"最坏情况"——即最大可能长度(比如 2048 token)——预留一整块连续显存。麻烦由此而生,论文拆成三种浪费:

- **内部碎片**:按 2048 预留,请求实际只生成了 10 个 token,剩下 2038 个 slot 的空间在整个请求生命周期里被占着却永远用不上。
- **预留浪费(reserved)**:哪怕这些空间最终会被填,但在被填之前它一直被这个请求"锁定",别的更短的请求想借用一段也借不到。
- **外部碎片**:每个请求预留的块大小不一,像停车场里大小不一的车位,中间那些不上不下的缝隙谁也停不进去。

这就解释了那个刺眼的数字:显存不是被算法吃掉的,是被"为了连续、为了保险而预留"的留白空耗掉的。而更值钱的东西被卡住了——因为 batch size(同时处理的请求数)直接受限于 KV cache 能塞多少,浪费显存等于直接压低吞吐。有人提过"整理碎片"(compaction),但对动辄上 GB 的 KV cache 做搬移,在延迟敏感的在线服务里代价太大,不现实。

到这里,问题已经很清楚:有没有办法让 KV cache 不必连续、不必预留,用多少给多少?

## 它真正看见了什么

新判断一句话:**KV cache 不需要连续,一个"逻辑连续、物理离散"的映射层就能把留白挤到几乎为零,还顺手打开了跨请求共享的门。** 这套思路直接借自操作系统的虚拟内存——把块当页(page)、把 token 当字节(byte)、把请求当进程(process)。

顺着这条链把承重概念接起来:

**物理块 / 逻辑块(physical/logical block)的分离**,是整个设计的地基。把每个请求的 KV cache 切成固定大小的**KV block**(比如每块装 16 个 token 的 key/value)。请求看到的是一串从左往右填充的**逻辑块**,以为自己的缓存是连续的;而它们实际落在显存里哪个物理位置,由一张 **block table(块表)** 决定——表里每一项记着"这个逻辑块对应哪个物理块、填了几个位置"。这一层翻译带来两个直接后果:物理块**按需分配**,只有当前一块填满才申请下一块,所以一个请求的浪费被死死限制在**最后一块之内**(最多半块),内部碎片几乎消失;又因为**所有块一样大**,不再有大小不一的缝隙,外部碎片被彻底消除。

**PagedAttention** 是让上面这层分离能真正跑起来的那块计算内核。传统注意力算子假设 key/value 在内存里连续排布;而现在它们散在不连续的物理块里。PagedAttention 改写了注意力计算,让它能**逐块取数**:算 query 与哪一块的 key,就去块表查那一块的物理地址取过来,算完再取下一块。没有这个内核,"物理离散"就只是个存储技巧,注意力算不动;有了它,离散存储才对上层透明。

概念接成最小模型:

```text
请求进来(长度未知)
   -> 不再预留最大长度,只按需申请物理块
   -> 逻辑块从左往右填,填满一块才申请下一块
   -> block table 记录逻辑->物理映射
   => 每个请求浪费 <= 一块; 有效显存逼近满格
   => 同批能塞更多请求 -> 吞吐 2-4x
```

**回到原锚点**:那 60%~80% 的浪费,来自"预留 + 三种碎片"。按需分配把预留和内部碎片压进最后一块,统一块大小消掉外部碎片,于是利用率从 20%~38% 跳到 96%(论文 Fig. 2),batch 变大,吞吐随之翻倍。这较稳地成立——论文在 13B/66B/175B 三种规模、ShareGPT/Alpaca 两种真实长度分布上,对比 FasterTransformer 与 Orca 都显示 2-4× 吞吐提升,且**不影响模型精度**(只改显存布局,不改计算结果)。

**区分一个邻近情况**:同样是"细粒度 batching",Orca 用的是 iteration-level scheduling(每轮迭代动态增删请求),它解决的是**计算和排队**的浪费——让新请求不必等整批算完。但 Orca 仍然给每个请求预留连续显存,所以它没碰**显存留白**这个瓶颈。这解释了为什么二者叠加才是完整答案:一个省算力空转,一个省显存留白。论文把 batch 能塞多少的瓶颈明确归到显存(memory-bound),而非算力。

**改变一个条件**:如果把块调大会怎样?块越大,一次能并行处理的 token 越多,内核利用率越高、延迟越低;但"每个请求最多浪费一块"里的这"一块"也变大了,碎片回升。所以块大小是个 trade-off——这也从反面印证了整套机制的因果:浪费的下界正是**一块**的大小。

分离层还顺手打开了**共享**这扇门——这是旧系统连想都没法想的,因为它们的缓存锁死在各自的连续空间里。既然逻辑块到物理块是多对一的映射,就能让多个序列的逻辑块**指向同一个物理块**,再配一个 **reference count(引用计数)** 和 **copy-on-write(写时复制)**:

- **并行采样**:一个 prompt 采样出多个候选,prompt 部分的物理块被多个序列共享(引用计数为采样数);只有当某个序列要往共享块里写自己的新 token 时,才复制出一份独立块,引用计数减一。共享 prompt 越长,省得越多。
- **束搜索(beam search)**:候选之间不仅共享 prompt,还共享中间生成的块,且共享结构随解码动态变化。旧系统在束之间要频繁整块拷贝 KV cache;vLLM 里绝大多数块直接共享,写时复制每次只拷一块。
- **共享前缀 / system prompt**:多个请求共用一段长指令前缀,服务方可以预先算好这段的 KV cache 存成物理块,新请求把逻辑块直接映射过去,prompt 阶段只需算自己那部分输入。

这套共享同样有分寸:它省的是**存储和重复计算**,自回归生成阶段各序列结果不同,那部分不能共享。论文报告并行采样、束搜索场景下最高可省约 55% 显存——这是"在这些解码算法下"的结论,不是普遍规律。

最后一块拼图是**抢占(preemption)**:请求太多、物理块耗尽时怎么办?vLLM 用 FCFS(先到先服务),需要腾地时先赶最晚到的请求。因为一个序列的所有块总是一起被访问,它用**全有或全无**的驱逐策略(一个序列要么全踢要么不踢);同一请求下的多个序列(如束候选)作为一个 sequence group 一起调度。被踢的块有两条回收路:**换出到 CPU 内存**(类似 OS 的 swap,受 GPU 显存上界约束),或**重算**(把已生成 token 接回原 prompt,一次 prompt 阶段就能重建全部 KV cache,常比原始逐字生成更快)。选哪条取决于 CPU-GPU 带宽与算力的相对高低。

> **背景概念**:本文反复说的"物理块""显存""换出到 CPU"分别落在 GPU 内存层次的哪一层,以及 register/shared memory/L1/L2/HBM/CPU RAM 的完整关系,单独整理在 notes/20260813T183934--gpu-memory-hierarchy__concept.md。这里只留和本文直接相关的三点结论:

- vLLM 的**物理 KV block 默认住在 HBM(GPU DRAM,即"显存")**——论文 4.2 节明说 block engine "allocates a contiguous chunk of **GPU DRAM** and divides it into physical KV blocks"。所以前面讲的"显存留白""利用率 20%~38%",量的都是 HBM。
- **抢占换出**时,被踢的块从 HBM 复制到 **CPU RAM**(论文所说的 swap),需要时再搬回;代价取决于 HBM↔CPU RAM 之间那道"数十 GB/s"的窄门。
- **SRAM 在本文没直接出场**——它是 FlashAttention 那类优化的战场:FlashAttention 优化 HBM↔SRAM 的**搬运**(省带宽),PagedAttention 优化 HBM 内部的**排布**(省容量),二者作用在不同层、可以叠加。

## 我能带走什么

> 以后看到"显存不够、batch 上不去、想换更大的卡",我先不急着判断"是算力/容量不够",而先问:**这块显存是真的装满了有效数据,还是被"预留最大长度 + 碎片"浪费掉了?**

这条判断规则可迁移到任何"资源按最坏情况预分配、实际用量远低于上限、且不可回收"的场景——不只 KV cache。识别信号是:**资源利用率数字很低,但系统却报告"不够用"**。这几乎总意味着分配粒度太粗、或预留策略太保守,而不是资源总量不足。

更深一层的启发是这篇论文的方法论本身:当一个新领域(LLM 服务)撞上老问题(内存碎片与共享),不必从零发明,先问**操作系统几十年前是怎么解决同构问题的**——虚拟内存、分页、写时复制、swap,这套成熟抽象往往能整体平移,前提是你愿意为它改写底层算子(这里是把注意力内核改成能逐块取数)。
