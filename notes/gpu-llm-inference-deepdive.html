0 · 这一篇要回答什么

上一篇用“一枚 token 进卡”讲清了 prefill vs decode、HBM 带宽和 batch 杠杆。这篇往更深处走，回答几个更具体的问题：

  • LLM 有几十层，每一层里面到底是什么？是不是每层都有一套完整的 attention + MLP？
  • 模型在 GPU 上并不是一个整体，而是被拆成很多 kernel。kernel 启动时定义的 grid → block → warp → thread 层次，是如何落到 SM、Tensor Core、共享内存上的？
  • prefill / decode 是推理阶段，attention / MLP 是每一层里的两类子层，它们不是并列的“阶段”。本篇会分别说清：每个阶段里 attention 和 MLP 分别卡在 GPU 的哪个部件上，为什么优化 inference pipeline 的人总在说“带宽”“融合”“通信”？
  • 从单卡到多卡再到 MoE，数据流和瓶颈会发生什么变化？

目标读者：已经知道 Transformer 大概怎么算，但不太清楚 GPU 底层执行模型的人。

1 · 先补模型结构：Transformer 层到底长什么样

先回答最基础的问题：LLM 不是“一个大网络”，而是同一个模块叠很多次。通常说的 7B、13B、70B 模型，基本结构是：

token 序列 → embedding → [ Layer 1 → Layer 2 → … → Layer N ] → final norm → lm_head（映射到词表） → softmax/采样 → 下一个 token

这里的 Layer 就是我们常说的 Transformer block / decoder layer。每一层都是一个完整的 attention 子层 + 一个完整的 MLP 子层，外面再套残差连接和归一化。也就是说：

Layer 1（下面这个结构会原样重复 N 次）
① Attention 子层 QKV 投影 → 注意力计算 → 输出投影
作用：让每个 token 从上下文里“收集信息”
② MLP 子层 升维 → 激活 → 降维（Llama 风格为 gate/up/down）
作用：对每个 token 做独立非线性变换
前置/后置残差 + RMSNorm/LayerNorm 通常也在这里
▼ Layer 2（同一套结构，但参数不同）
▼ …
▼ Layer N（同一套结构，但参数不同）

所以“每个 layer 都有一份完整 attention + 一份完整 MLP”是对的。不同 layer 的参数互不共享；这也是模型参数量大的主要原因。例如一个 7B 模型，绝大部分参数来自每一层里的 QKV 投影、输出投影、MLP 升维/降维矩阵，以及最后的 lm_head。

1.1 · 一个 Dense Transformer 层里的参数与张量形状

以常见 Llama/Qwen 风格为例（忽略 GQA/MQA 细节，先看主线）：

x: [batch, seq, hidden] Attention 子层: q = x @ Wq # [batch, seq, num_heads * head_dim] k = x @ Wk # 同上 v = x @ Wv # 同上 attn = softmax(q @ k^T / sqrt(d)) @ v out = attn @ Wo # [batch, seq, hidden] MLP 子层（Llama 风格）: gate = x @ Wgate up = x @ Wup down = SiLU(gate) * up @ Wdown # 也有更简单的 MLP: down(act(up(x))) out = x + attn_out out = out + mlp_out

注意：每一层都是这样一组 GEMM/GEMV + attention + 非线性。LLM 推理时，prefill 和 decode 都会把这一套按顺序走完；区别只是当前批量里有多少 token、矩阵的形状是“大乘大”还是“大乘小”。

2 · 模型参数在 GPU 里住在哪

上一篇讲过内存金字塔，这里直接落到推理场景。一张 H200 的典型资源大致是：

寄存器
每个 SM 几十 KB ~ 256KB 级，单线程私有，最快
shared memory / L1
每个 SM 约 256KB 级，block 内共享，kernel 手动管理
L2
H200 约 50MB 级，所有 SM 共享，自动缓存
HBM3e
H200 141GB，约 4.8TB/s，权重/KV cache/激活值的主要仓库
H200 不是“一张卡算力特别猛”这么简单：它的 141GB HBM3e 容量和 约 4.8TB/s 带宽对 LLM 推理同样关键。算力上它延续 Hopper 架构，FP16 Tensor Core 稠密算力约 989 TFLOPS（与 H100 SXM 同款计算核心）。

一次前向中，GPU 需要“读”的东西分两类：

  • 权重（weights）：几十 GB，常驻 HBM。每个 token 每层都要读，decode 时每步几乎全读一遍。
  • KV cache：随序列长度增长，存在 HBM。attention 阶段要读历史 K/V。
  • 激活值（activations）：MB 到几百 MB 级，prefill 时会比较大，decode 时很小。

3 · 从模型到 kernel：CPU 负责翻译，GPU 负责执行

GPU 并不知道“Transformer”是什么。推理框架（vLLM、TensorRT-LLM 等）在 CPU 上把模型的计算图翻译成一串 CUDA kernel，再逐个发射到 GPU。一个 kernel 就是一段在 GPU 上运行的小程序，例如“算一个 GEMM”“算一次 FlashAttention”“算一次 RMSNorm”。

CPU / 框架 └─ 把每层算子编译成 kernel：GemmQKV、FlashAttention、GemmOut、GemmGate、GemmUp、GemmDown、RMSNorm、ResidualAdd… └─ launch kernel 到 GPU stream GPU └─ kernel 启动时定义 grid，grid 的多个 block 被分发到 SM 上执行 └─ 从 HBM/L2 读数据 → 在 SM 里算 → 写回 HBM/L2

因此“GPU 参与 LLM 推理”的本质是：CPU 编排 kernel，GPU 拼命把每个 kernel 跑快。性能优化很多时候就是减少 kernel 数量、减少 kernel 里的数据搬运、或让 kernel 更充分地利用硬件资源。

4 · Kernel 的微观世界：grid / block / warp / thread

一个 kernel 启动后，并不是“一个巨大的函数在 GPU 上从头跑到尾”。它定义了一个嵌套的并行层次：

Kernel（一段提交给 GPU 的程序/任务） └─ 启动时创建一个 Grid（线程格） └─ Grid 由多个 Block（线程块）组成 └─ Block 由若干 Warp 组成，Warp = 32 threads └─ Thread 是执行指令的单个线程

这里要区分两个不同层面的概念：kernel 是“被提交的任务”，不是执行单元；warp 是 SM 内部调度指令的粒度。连接关系是：CPU 发射 kernel 时，kernel 会定义一个 grid；GPU 上的 block 调度器把 grid 中的 block 分发到有空闲资源的 SM；SM 再把驻留在自己上的 block 中的线程按 warp 分组、逐条调度执行。所以不是说“kernel 直接切到 SM”，而是 kernel → grid → block 分发到 SM → SM 按 warp 调度 thread。

软件/逻辑视角：一次 kernel launch

Kernel └─ Grid（本次 launch 的“全部 block 的集合”，不是硬件） └─ Block（一个线程组，一个待执行的 work item） └─ Warp（32 个线程，SM 的调度粒度） └─ Thread

grid 就是这次 kernel 调用里所有 block 的总称；它只存在于“这次调用”的逻辑层面，不是一个芯片上的物理容器。

硬件/物理视角：执行资源

GPU └─ 多个 SM（物理执行单元） └─ warp scheduler（调度 warp） └─ thread cores / tensor cores

block 不是 SM 的固定子部件，而是被调度到 SM 上执行的“工作块”；一个 SM 可以同时驻留多个 block，block 做完后 SM 再接收新的 block。

所以“kernel → grid → SM → block”不准确：grid 和 block 是软件逻辑层，SM 是硬件资源层。正确映射是 kernel 的 grid 里有很多 block，硬件调度器把 block 分配到 SM；进入 SM 后，block 内部的 warp 才被调度执行。

那 block 为什么有“自己的 shared memory”？因为 block 并不是自己带着一块物理内存，而是当 block 被调度到某个 SM 上时，硬件会从该 SM 的物理 SRAM 中划出一部分给它作为 shared memory；block 结束或退出后，这部分归还给 SM，供下一个 block 使用。同样，thread 也不是一个独立的物理核心，它是逻辑执行上下文；真正物理的是 SM 里的执行单元、寄存器堆、shared memory、Tensor Core 等。warp 则是硬件把 32 个逻辑 thread 捆在一起调度的粒度。

一张 H200 的芯片侧视图（简化）

SM（Streaming Multiprocessor）× 很多个

Tensor Core FP32/INT32 Core shared memory / L1 Register File Warp Scheduler

每个 SM 能同时驻留多个 block，block 再以 warp 为单位被调度执行。

Warp = 32 threads

32 个线程一起执行同一条指令，但数据不同（SIMT）。如果分支发散，warp 会串行执行各分支，这是性能杀手之一。

Block = 若干 warp

block 内的线程可以通过 shared memory 协作、同步。block 之间不能直接共享 shared memory。

Tensor Core

专门做 4×4/16×16 这类小矩阵乘加（MMA），一次指令算一大块乘加，是 GEMM/GEMV 的算力来源。

数据流动：为什么“搬运”常比“计算”贵

寄存器
单线程私有，计算直接发生在这一层
shared memory
block 共享，GEMM/Attention 的分块数据放在这里复用
L2
跨 SM 共享缓存；KV cache 的复用常在这里体现
HBM
权重和长序列 KV 的主仓库，容量大但最慢

一个 kernel 的耗时常常由“从 HBM/L2 搬到 shared memory/寄存器”主导，而不是由 ALU 计算主导。理解这一点后，很多推理优化就变成“减少搬运 / 增加每次搬运后的计算量”。

Occupancy（占用率）就是“一个 SM 上能同时驻留多少 block/warp”。不是越高越好，但太低会让 SM 无法用并行隐藏访存延迟。LLM 推理中，decode 的 GEMV 往往不是卡 occupancy，而是卡 HBM 带宽。

5 · 具体 kernel 怎么映射到硬件

这一节看三个最重要的 kernel 类型：GEMM/GEMV、Attention、Norm/激活。理解了它们，就理解了 LLM 推理的大部分硬件行为。

5.1 · GEMM / GEMV：MLP 和投影层的真身

Transformer 里绝大多数计算是 矩阵乘法。例如 x @ W，x 是激活，W 是权重。GPU 上的 GEMM kernel 不会把整个大矩阵一次性塞进 SM，而是切成 tile（分块）：

Prefill 的 GEMM（大矩阵 × 大矩阵）
形状类似 [N_tokens, hidden] × [hidden, 4*hidden]

- 每个 block 负责输出矩阵中的一小块 tile
- 例如 128×128 输出 tile
- 数据分块从 HBM → L2 → shared memory
- Tensor Core 在寄存器里做 16×16×16 这类 MMA
- 计算密度高，SM 能吃饱
Decode 的 GEMV（矩阵 × 向量）
形状类似 [1, hidden] × [hidden, 4*hidden]

- 输出只有一行
- 每个 block 负责读取权重的一段行/列
- 计算量极小，但权重还是要全部读一遍
- 大部分时间在等 HBM 数据，Tensor Core 闲着
- 典型 memory-bound

映射到硬件上，GEMM 的经典做法是：

  • Block 级：把输出矩阵切成若干 tile，每个 block 负责一块，block 之间并行。
  • Warp 级：block 内再按 warp 切，每个 warp 负责 tile 里的一个子块。
  • Thread 级：warp 里的 32 个线程共同把数据从 shared memory 搬到寄存器，再交给 Tensor Core 做矩阵乘加。
  • shared memory 复用：A、B 的两个小分块先读到 shared memory，算完一小块再换下一块，避免每个数都从 HBM 读。
decode 时 GEMM 退化成 GEMV（M=1），权重矩阵仍然巨大。无论 kernel 切得多好，必须把整份权重从 HBM 读一遍这个物理事实不会消失。这也是“decode 卡带宽”的根本原因。

5.2 · Attention：FlashAttention 和 KV cache 的硬件逻辑

Attention 子层除了 QKV 投影是 GEMM，核心的“注意力计算”也是一个专门 kernel。它的数据访问模式比普通 GEMM 更特殊：每个 token 都要看所有历史 token 的 K/V。

Q: [batch, heads, seq, head_dim] K: [batch, heads, seq, head_dim] # 长序列时 K/V 就是 KV cache V: [batch, heads, seq, head_dim] 对每个 query： scores = Q @ K^T probs = softmax(scores) out = probs @ V

朴素实现会把 scores 和 probs 写回 HBM，再读回来。这会浪费大量带宽。FlashAttention 的硬件思想是：

  • 把 Q、K、V 都切成小块，在 shared memory 里分块计算，避免把中间 scores 写回 HBM。
  • 用 online softmax 技巧边算边更新归一化统计量，不必等全部 scores 算完。
  • 每个 block 负责一个 query 块，K/V 块不断从 HBM/L2 流入 shared memory，在片上完成“读一次、算多次”。

在 decode 场景，Q 只有 1 个 token，但需要读取之前所有 token 的 K/V。此时 attention kernel 的瓶颈不是算力，而是从 HBM/L2 读 KV cache 的带宽。KV cache 越大，每一步读取越贵。

所以 GQA（Grouped-Query Attention）的动机也清楚了：减少 K/V 头数 = 减少 KV cache 的存储和读取量，对 decode 带宽非常友好。

5.3 · Norm、残差、激活：小而频繁的 memory-bound kernel

每一层还有 RMSNorm / LayerNorm、残差相加、SiLU/GELU 激活。这些算子计算量很小，但每次都要把张量读一遍、写一遍，所以通常也是 memory-bound。性能优化喜欢把它们 融合 到前后 GEMM kernel 里，减少 HBM 往返。

不融合：GEMM → 写 HBM → 读 HBM → 加残差 → 写 HBM → 读 HBM → RMSNorm → 写 HBM … 融合后：一个 kernel 里顺便完成 epilogue（残差、Norm、激活），少几次 HBM 读写

这也是推理框架里“算子融合（operator fusion）”最直接的价值。

6 · prefill vs decode：同一套模型在不同推理阶段，瓶颈如何变化

先把维度对齐：prefill / decode 是同一模型在自回归生成中的两个阶段；attention / MLP 是每个 layer 内部的两个组成部分。这两个维度不是并列关系——prefill 阶段要跑 attention + MLP，decode 阶段也要跑 attention + MLP。下面比较的是同一套 attention+MLP 在两种阶段下的瓶颈差异。

Prefill（预填充）compute-bound

  • 一次处理整段 prompt，例如 2048 个 token。
  • GEMM 是大矩阵乘，Tensor Core 占用率高。
  • 权重从 HBM 读一遍，但被 N 个 token 的计算摊薄。
  • 瓶颈通常：算力 / SM 吞吐 / L2 到 shared memory 的搬运。
  • 对应指标：TTFT（首 token 延迟）。

Decode（解码）memory-bound

  • 每步只生成一个新 token，自回归循环。
  • GEMM 变 GEMV，Tensor Core 利用率很低。
  • 每步仍要读全部权重 + 读 KV cache。
  • 瓶颈通常：HBM 带宽 / KV cache 带宽。
  • 对应指标：TPOT / ITL（每 token 延迟）。

拿 7B Dense 模型 FP16 在 H200 上做 batch=1 decode 的粗略时间账：

搬权重 14GB / 4.8TB/s
~2.9 ms（每步下限）
计算 14 GFLOP / 989 TFLOPS
~0.014 ms（算力几乎空转）

推导链：每步需要读一遍约 14GB 权重 → 带宽时间 ≈ 14GB ÷ 4.8TB/s ≈ 2.9ms；每步计算量 ≈ 2 × 7B ≈ 14 GFLOP → 计算时间 ≈ 14GFLOP ÷ 989TFLOPS ≈ 0.014ms；带宽时间远大于计算时间，所以瓶颈在 HBM 带宽。batch=1 时，无论 kernel 写得多好，decode 都被“每步读一遍 14GB 权重”钉死在 ~2.9ms 附近。量化到 INT8/FP8 后权重变小，这个下限才会直接下降。

7 · Batch 如何改变硬件行为

decode 的救星是 batch：让多个请求在同一个 decode step 里一起算。此时每一层的权重仍只读一次，但计算量变成 B 倍。用 H200 的 7B 例子：

B=1
读权重 ~2.9ms，算 ~0.014ms → 带宽浪费
B=64
读权重 ~2.9ms，算 ~0.91ms → 仍卡带宽
B=256
读权重 ~2.9ms，算 ~3.6ms → 翻转成算力瓶颈

粗略交叉点：B ≈ 2.9ms ÷ 0.014ms ≈ 207。也就是说，在只考虑权重读取和计算时，B 要超过 200 左右才真正从带宽瓶颈翻到算力瓶颈；实际还会叠加 KV cache 读取、launch、通信等开销。

vLLM 的 continuous batching 就是每一步动态把“正在 decode 的请求”拼在一起，并允许新请求随时插入 prefill，让 GPU 尽量保持大 batch。

但 batch 不是无限大。一个硬约束是 KV cache 容量：每个请求的 K/V 随生成长度增长，batch 越大、序列越长，HBM 里 KV cache 占用越高。PagedAttention 就是解决“KV cache 在 HBM 内部如何不浪费”的经典方案。

8 · 从单卡到多卡：模型装不下/算不动时怎么拆

当模型超过单卡显存，或需要更高吞吐时，就要把模型/数据分布到多张 GPU。三种最基础的并行方式：

Tensor Parallel（TP）张量并行：把每一层的权重矩阵切成几份

  • 每张卡只存一层权重的一部分。
  • 同一个 GEMM 由多卡协作完成。
  • 在需要跨卡归约的线性层后（例如 attention 输出投影、MLP 降维投影）需要 AllReduce 汇总部分结果；并不是每个矩阵乘后都有。
通信点：每层多次 AllReduce → 对 NVLink 带宽敏感

Pipeline Parallel（PP）流水线并行：按层切

  • 第 1~N/2 层放 GPU0，后半层放 GPU1。
  • 数据像流水线一样从前往后传。
  • 减少单卡显存压力，但可能出现流水线气泡。
通信点：层边界 P2P 传输，频率低于 TP

Data Parallel（DP）数据并行：每卡一份完整模型

  • 每张卡独立处理不同请求。
  • 训练时需要梯度同步；推理时通常只是多副本负载均衡。
  • 最简单，但每卡都要放下完整模型。
推理时几乎没有卡间通信，但显存复制严重

实际推理系统常用组合，例如 TP + PP + DP：先张量切分把单层变小，再按层切分减少单卡层数，最后放多副本提高并发。多卡之间的通信走 NVLink / NVSwitch（单机）或 RDMA/PCIe（跨机），通信本身也会成为瓶颈。

多卡推理的思维切换：单卡优化主要盯 HBM 带宽和 SM 利用率；多卡优化还要盯 通信量、通信频率、负载均衡。Tensor Parallel 能减小每卡读权重的时间，但 AllReduce 可能吃掉省下的时间。

9 · Dense 之后：MoE 给 GPU 带来的新挑战

前面讲的都是 Dense Transformer：每个 token 在每一层都会经过同一个完整 MLP。MoE（Mixture of Experts）则把 MLP 换成一堆“专家”小网络，每个 token 只经过其中少数几个专家。

Dense MLP

  • 每个 token 必须算全部 MLP 参数。
  • 计算量约 = 2 × 参数量 × token 数（FLOPs），稳定可预测。
  • 硬件行为：大 GEMM，权重全部读。

MoE MLP sparse activation

  • Router 先给每个 token 选 top-k 专家。
  • 只有被选中的专家参与计算，总计算量下降。
  • 但所有专家权重仍可能放在 HBM 里，显存占用大。
  • token 到专家之间需要 dispatch/combine，甚至跨卡 All-to-All。

从 GPU 视角看，MoE 不是简单“省了计算”：

  • Router 通常是一个小 GEMM + TopK，单看算力占比不大，但它决定后续 token 如何重排，可能间接影响访存和通信。
  • Token Dispatch：把 token 按专家分组、重排，再送给对应专家 kernel。数据搬移可能很贵。
  • 专家并行（EP）：把不同专家放到不同 GPU。某个 token 要去别的卡上的专家时，就需要 All-to-All 通信。
  • 负载不均：热门专家可能收到过多 token，导致某些 GPU 忙、某些 GPU 闲。
MoE 的硬件本质：用“稀疏计算 + 更灵活的通信/调度”换取“更少的 FLOPs”，但代价是更复杂的显存布局、访存模式、通信模式和负载均衡。优化 MoE 推理，常常不只是优化 GEMM，而是优化 token 路由、专家分派、通信重叠。

10 · 把常见优化动作挂回硬件

现在可以建立一张“硬件定位图”。看到任何推理优化，先问它作用在哪一层：

a. 省 HBM 容量 / 省 KV cache

  • 权重量化：14GB → 7GB/3.5GB，decode 带宽下限直接下降
  • PagedAttention：KV cache 分页，减少碎片浪费
  • GQA / MLA：减少 KV cache 体积

b. 提高每次读带宽的收益

  • Continuous batching：加大 decode batch
  • Prefix caching：复用已算过的 KV
  • Speculative decoding：用小模型草拟多个候选 token，再让目标模型一次前向验证/接受

c. 减少 HBM ↔ shared memory 往返

  • FlashAttention：中间矩阵留在片上
  • 算子融合：Norm/残差/激活并进 GEMM epilogue
  • 更好的 tiling：提高 shared memory 数据复用

d. 减少 CPU 发射 / 通信 / 等待

  • CUDA Graph：把几百次 kernel launch 压成一次
  • 多流并行：prefill 和 decode 重叠
  • TP/EP 通信优化：减少 AllReduce / All-to-All 次数或做通信隐藏

11 · 一张图记住“GPU 参与 LLM 推理”

模型层视角： prompt → 每层[Attention子层 + MLP子层] × N → lm_head → token GPU 视角： CPU 调度 → 发射 kernel → grid 的 block 分发到 SM → SM 按 warp 调度 thread └─ 每个 kernel 都在做同一件事： 从 HBM/L2 搬数据到 shared memory/寄存器 → 用 Tensor Core/CUDA Core 算 → 写回 瓶颈视角： prefill：大矩阵乘多 → compute-bound → 盯 Tensor Core / SM 利用率 decode：权重和 KV 反复读 → memory-bound → 盯 HBM 带宽 / KV cache 带宽 batch：把权重读一次变成服务 B 个 token → 把带宽瓶颈转回算力瓶颈 多卡：把单卡 HBM 装不下的模型拆开 → 新增通信瓶颈 MoE：减少计算但增加调度/通信/显存复杂度 → 瓶颈可能从算力移到路由和 All-to-All

带走：

  • LLM 是同一个 Transformer 层叠很多次；每一层都有一个完整 attention 子层 + 一个完整 MLP 子层。
  • 注意维度：prefill / decode 是推理阶段，attention / MLP 是每层内的子层，不是四个并列的“阶段”。
  • GPU 被提交的最小独立任务是 kernel，但 kernel 不是执行单元；SM 的指令调度粒度是 warp（每个 warp 内 32 个线程并行执行同一条指令）。完整链路是 kernel → grid → block 分发到 SM → SM 按 warp 调度 thread。
  • MLP/投影层是 GEMM/GEMV，核心在 Tensor Core 和 shared memory tiling；attention 的核心在 KV cache 访问和 FlashAttention 分块；Norm/残差/激活是小型 memory-bound kernel，适合融合。
  • prefill 卡算力，decode 卡带宽；batch 是把 decode 从带宽困境拉出来的主要杠杆。
  • 多卡引入通信瓶颈，MoE 引入调度/All-to-All 复杂度——优化永远要问：当前瓶颈在 HBM、L2/shared memory、Tensor Core、还是通信？
