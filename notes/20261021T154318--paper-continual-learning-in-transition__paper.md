# 持续学习：从防遗忘到管能力

**副标题**: Continual Learning in Transition（把持续学习从“后训练改参数”重画成 When–Where–How 三轴：能力何时更新、放在哪、怎么写，以及每次写入会扰动什么）

**作者**: Zhiyan Hou, Dan Zhang, Tao Feng, Liyuan Wang, Wei Li, Xiangzhao Hao, Hongyan An, Junfeng Fang, Haokai Ma, Zhaohui Xu, Xinyu Tang, Haiyun Guo, Jinqiao Wang, Tat-Seng Chua

## 速读

一个编程 agent 在项目里摸出一条构建优化：这次会话学会了，下次还在吗？放上下文，窗口一关就没；写进记忆，可能检索不到或被旧条目淹没；存成技能，换项目就可能不匹配；固化成规则，往往还是人改的；微调进参数，又可能冲掉旧能力。同一个“学会了”，落在不同地方，寿命、成本和失败方式完全不同。经典持续学习只回答了其中一格：后训练、off-policy 梯度、参数，主要问题是灾难性遗忘；这篇综述把格子拆成 When/Where/How（何时、何地、如何）三轴，把持续学习重新定义为“能力的持续演化”。它真正多看见的是：关键不只是更新算得对不对，而是这次更新把能力写到了哪里、什么时候写、会扰动哪些旧能力；遗忘也因此有参数覆盖、记忆衰减、上下文溢出、技能/协议失配等多张脸。作者进一步判断：harness（模型外的记忆、技能、协议）工程可以在功能上替代一部分持续学习，但还没有在机制上构成它；真正的考验是长程 agent。以后看一个“会学习”的系统，我先问：它把什么写进哪个载体，凭什么保证下次还能用，又怎样避免把旧能力弄坏？

## 它到底在解决什么

还是那个构建优化。假设 agent 在一个大型项目里试错很久，终于发现“先改这个配置，再清那个缓存，构建时间能减半”。这条经验至少有三部分：一个事实（这个项目有这个问题）、一个过程（先改配置再清缓存）、一个适用边界（只在这个代码库、这个版本成立）。它应该被记在哪里？

- 只放在上下文里：本次会话有效，会话结束就没了；就算上下文很长，压缩摘要也可能把“为什么”丢掉，下一次只留下一个看似武断的步骤。
- 写进外部记忆：可以跨会话，但下次要检索得到；条目多了会互相干扰，旧条目会过期，检索分数会漂移。
- 存成技能：可以执行、可以组合，但技能绑定了当时的工具、路径和项目结构，换一个仓库就可能不匹配。
- 写进参数：最稳定，也最容易迁移到相似任务；但一次全量微调可能把旧能力覆盖，而且成本最高。
- 改成规则/协议：人可以直接编辑，但“谁在改”往往是工程师，不是系统自己从经验里学。

这个例子不是论文的实验，而是把论文的三条轴压到一个具体动作上：**同一个能力，载体不同，持续学习的含义就不同。** 论文要解决的，正是旧分类法说不清这件事。

经典持续学习的标准设定是：任务按顺序到来，旧数据不可见或只能以受限形式访问，模型在这种情况下更新参数，目标是在学新任务的同时，把旧任务的损失保持住。核心障碍是灾难性遗忘：新任务的梯度会改动支撑旧任务的表示和决策边界。围绕它，文献形成了回放、梯度投影、架构隔离/扩展、正则化四类方法，评价指标是稳定性–可塑性权衡、向后/向前迁移。

这套框架隐含了三个“固定答案”：

1. **When**：学习发生在部署前的专门训练阶段；
2. **Where**：能力主要存放在模型参数里；
3. **How**：更新由外部提供的数据上的梯度下降驱动。

在经典设定里，这三个答案太自然，以至于没人把它们当问题。但大语言模型（LLM）时代的方法一个个把答案变成了变量：on-policy RL 在改数据来源；test-time training（测试时训练）把学习推到推理时；Voyager 的技能库、Promptbreeder 的 prompt 演化、MemoryBank 的记忆写入，则把能力放到参数之外。它们不是旧四类里的新成员，而是把“学”的对象从模型参数扩展成了系统能力。旧分类法不是错了，是覆盖不到这些新坐标。

所以论文换了一个问法：**能力在什么时候演化、在哪里积累、用什么机制更新？** 这三个问题分别对应 When、Where、How。经典 CL 不是被否定，而是被放回坐标系的某个点：后训练 × 参数 × off-policy 梯度。标题里的 transition，指的不是某个模型升级，而是持续学习的单位从模型参数转向系统能力。

这篇综述的贡献不是新算法，而是坐标系；它没有跨方法的统一实验，证据主要是方法结构的相似性、个别实证结果和 benchmark 覆盖。

## 它真正看见了什么

一句话：**持续学习是“把能力写到某个载体、并让它在以后还能被调用”的过程；三轴决定这次写入的时机、位置和方式，而贯穿三轴的核心约束是——这次写入会把已有能力推多远。**

先看 When。它不只是“训练还是推理”的时间标签，而是决定**反馈什么时候出现、系统能等多久、写完要不要持久化**。

- **预训练**：数据是无标注的语料流，任务边界变得模糊，学习单位从“任务”变成“语料分布的变化”。SimpleCPT 的做法很工程：学习率重新升温，加一小块基础分布 replay，405M 和 10B 模型吸收新语料后，原分布上的退化接近可忽略。它说明持续预训练不必推倒重来，但也说明“小 replay + 升温”这种简单配方在更大模型、更强分布偏移下是否够用，还没有答案。
- **后训练**：监督微调（SFT）→ 偏好优化或带可验证奖励的强化学习（RLVR）变成一条纵向流水线，每一轮都可能侵蚀上一轮。TRACE 的顺序指令微调显示，旧任务性能、通用能力、指令遵循、安全对齐都会掉；更细的诊断指出，其中一部分是“假遗忘”——任务对齐丢了，但底层知识还在，冻住底部层能缓解。这里的关键不是“又有一个 benchmark”，而是**后训练流水线本身就是持续学习的单位**，不能只看单次微调。
- **推理时**：最关键的区别是**持久化**。search、self-consistency、test-time scaling 能让当前答案更好，但一般不会留下持久改变；测试时训练（TTT）里的 TTT-LM 把测试序列写进快速权重（fast weights，推理时临时更新的权重），测试时强化学习（TTRL）用模型自己采样出的奖励信号更新，推理过程中系统已经被改写。只有后者才是推理时的持续学习。这个区分看似抠字眼，实际上决定了系统有没有“下次”。

再看 Where。论文把载体分成参数和 harness 两大类；harness 再分三类：

- **参数**：仍是经典载体，但内部也在分块。全量微调、LoRA（低秩适配）、O-LoRA 的正交子空间、LoRAMoE 的专家路由、MemoryLLM 的可写记忆池，都是把一个大参数空间拆成局部可更新模块，用结构隔离换更小的跨任务干扰。它们改变的是参数载体的粒度，不是载体本身。
- **记忆（memory）**：跨调用可读写的事实、经历、上下文。MemoryBank 用艾宾浩斯式遗忘曲线做长期记忆，A-MEM 把读写粒度降到原子命题，MemRL 用奖励驱动记忆更新。它解决的是“事实和经历放在哪”，不是“参数怎么改”。
- **技能（skills）**：可执行、可组合的过程性能力。Voyager 让 agent 写代码、存进技能库、在环境里复用；SkillRL/SAGE 让技能库和策略一起在奖励下演化。它解决的是“过程放在哪”，而且技能的离散性让新旧任务不必挤在同一片参数里，天然降低了干扰。
- **协议（protocols）**：规定模型如何与环境交互的规则、格式、prompt。Promptbreeder 让 LLM 改写 prompt 本身，甚至改写“如何改写 prompt”的规则，把系统提示变成可演化载体；Cline/Aider/Cursor 的规则文件则是人把它当载体在改。它解决的是“行为框架放在哪”，但也是三类里研究最不成熟的。

这里有一个容易被忽略的区分：**载体不等于学习者。** 一个静态工具列表、一份人写的规则文件，确实把能力放在了模型外，但更新它的是人，不是系统从自身经验里闭环学习。论文在第四节把这点挑明：harness 工程在功能上完成了一部分持续学习，但在机制上还不是。判断标准不是“有没有外部文件”，而是“系统有没有根据交互反馈，自己改写这个文件，并让下一次行为变好”。论文点名的闭环例子是 Promptbreeder、Voyager、AgentEvolver 等少数，论文认为它们的更新机制不是演化搜索就是 RL，评测、稳定性、复现都还不成熟。

这更多是作者的立场，不是共识。反方观点是：更多上下文、更多计算、多模型 + 记忆 + 检索，可能在行为上等效于持续学习，不必让模型像人一样内化；论文自己把这场争论摆出来，并明确站在“功能替代、机制未替代”一边。

最后看 How。它问的不是“有没有用梯度”，而是“更新信号从哪里来，更新会把策略推多远”。

- **Off-policy 梯度**：数据来自历史 replay、静态语料、旧模型/教师的输出，和当前策略解耦。好处是信号稳定、可复用；坏处是训练分布可能离模型自身很远，模型被推到一个陌生分布上，旧能力更容易被破坏。SDFT 的办法是让模型先把任务数据改写成自己分布内的回答，再在这份“像自己”的数据上微调，用分布对齐来减小漂移。
- **On-policy 梯度**：数据由当前策略自己生成，再由奖励（reward）打分，基于人类反馈的强化学习（RLHF）和 RLVR 是代表。它对持续学习的意义是结构性的：论文引用的一项分析显示，遗忘程度与“新策略相对更新前策略（参考策略）的 KL 散度”有关（可以把 KL 散度理解为两个策略分布差多远）；如果新任务有很多个解，on-policy RL 会倾向于选一个 KL 更小的解，所以“学会新任务”与“少偏离旧策略”可以被同一个优化过程绑在一起；off-policy SFT 则可能收敛到离参考模型很远的分布。这是“为什么 on-policy 可能更少遗忘”的机制解释，不是“on-policy 一定不遗忘”的保证。TTRL 把同一原则搬到推理时，用模型自己多数投票得到的奖励来更新。
- **无梯度**：模型合并不碰历史数据，直接在权重空间做权重组合，以任务向量（task vector，微调权重减去基座权重）的加减为代表（Task Arithmetic、TIES、AIMMerging）；零阶（zeroth-order）方法只用前向计算估计下降方向（MeZO、ZeroFlow），其中 ZeroFlow 报告其隐式平滑在遗忘基准上不输甚至优于一阶微调；启发式学习（heuristic learning）/ 提示词演化（prompt evolution）则直接改外部对象（Reflexion 的反思记忆、Promptbreeder 的 prompt）。它们的共同点是：不计算解析梯度，但仍在“写能力”，也仍在“扰动旧能力”，只是扰动的位置和形式不同。

把三轴接起来，可以得到一个比“分类表”更有用的模型：

```text
能力要更新
  ├─ When: 预训练 / 后训练 / 推理时
  │        反馈何时到？要跨会话保留吗？
  ├─ Where: 参数 / 记忆 / 技能 / 协议
  │        写入多贵？多稳？能迁移吗？
  └─ How: off-policy / on-policy / 无梯度
           这次更新把旧能力推多远？
        ↓
  新能力写入 + 旧能力受扰
        ↓
  短期：学会了吗？长期：还记得吗？
```

这个模型是我把论文的 How 轴论证往外推的读法；论文本身主要给坐标系，没有把它形式化成一条定律。

这个模型最重要的推论，是载体之间的**权衡**，而不是“越外置越先进”：

| 载体 | 写入成本 | 容量/寿命 | 主要失效方式 | 迁移性 |
|---|---|---|---|---|
| 参数 | 最高，要梯度/对齐数据 | 容量随模型规模，写入后最稳定 | 灾难性遗忘、跨任务干扰 | 较高，内化后能跨情境 |
| 外部记忆 | 低，一次写入 | 受存储和检索带宽限制，会老化 | 检索衰减、旧条目污染、跨会话不一致 | 较低，绑定检索上下文 |
| 技能库 | 中，要验证/调试 | 可增长，但会膨胀、失配 | 与工具/项目结构失配、组合错误 | 较低，绑定执行环境 |
| 协议/规则 | 低，可直接编辑 | 易改也易漂移 | 规则冲突、情境变化后过时 | 较低，绑定交互情境 |
| 上下文 | 最低，直接塞 | 硬长度上限，注意力会稀释 | 溢出、压缩丢信息、注意力分散 | 几乎不迁移，会话结束即失 |

上下文不是 harness 的正式三类之一，而是论文 §4.1 单独讨论的最外层载体；放进同一张表，是为了把“写在哪”的完整代价一起看。

这张表是论文 §4.1 的“三层载体”与 §4.2 的“harness 迁移性”压在一起的结果：能力越往外放，写入越便宜、越可解释，但召回稳定性、可管理性和跨情境迁移性越差。参数不是被淘汰的那一端，它是用高写入成本换高稳定性和高迁移性的；harness 不是“免费的学习”，它是用低成本和可解释性换上下文绑定和检索脆弱性。真正的设计问题不是选边，而是**什么能力应该待在哪一层**。

这张表还解释了为什么论文说遗忘至少有“四张脸”：参数层是灾难性覆盖，记忆层是检索衰减和条目老化，上下文层是溢出和注意力稀释，技能/协议层是情境漂移后的失配。它们的时间尺度、可观察性、可逆性都不同；所以不能用同一个“遗忘率”去量所有载体，也不能只在参数层做稳定性–可塑性权衡。作者因此建议把遗忘从“灾难”改写成“主动压缩与释放”：哪些该留、哪些该忘、以什么速度忘，本身就是能力管理的一部分。

不过，三轴不是[严格笛卡尔积](<../Terms/Concept/Strict Cartesian Product.md>)。论文用组合画像（profile）而不是坐标点：Reflexion 是推理时 + 记忆 + 无梯度，TTRL 是推理时 + 参数 + on-policy，AgentEvolver 是参数 + 记忆 + on-policy，SKILL0 则是“技能库 → 参数”的迁移轨迹。一个方法可以同时落在多个轴上，也会随时间换位置；所以 Figure 2 只放了挑选出的代表方法，不是文献计量，空区域不能当成“没人做过”的证据。三轴标签也非互斥，论文按最显著的轴打主标签；覆盖只到投稿前，快速迭代的领域会漏新工作。

用这个模型回看锚点，三件事就清楚了：

1. **同一条构建经验，放在不同载体，失败方式不同。** 放上下文，失败是“会话结束/压缩丢理由”；放记忆，失败是“下次检索不到/被旧条目带偏”；放技能，失败是“换项目后不匹配”；放参数，失败是“旧项目的能力被覆盖”。这不是四种实现细节，而是四种持续学习问题。
2. **它能把“检索增强生成（RAG）”和“推理时持续学习”区分开。** 两者都在推理时引入外部信息，但无写回的固定语料 RAG 不因这次使用而改变下次；TTT/TTRL 会把这次的信息写回状态/参数，改变下次。前者是“查资料”，后者才是“学习”。同理，test-time scaling 不是 TTT：前者只花更多计算，后者留下持久变化。
3. **改一个条件，能预测压力往哪走。** 如果这条经验在多个项目里反复出现、且跨项目通用，那么每次靠检索/上下文携带就太贵、太不稳定，系统会被推向“固化进参数”；一旦固化，参数干扰和旧能力遗忘的风险上升，于是 on-policy/低 KL、LoRA 模块化、replay 这些“控制扰动”的手段变得重要。反过来，如果这条经验只在一个短期项目里成立、下个月就过期，把它写进参数就是浪费且有害，应该留在 harness，并设计主动遗忘/回收。**能力的通用性和过期速度，决定它该往哪层走；更新机制的选择，只是在为这次迁移控制扰动。**

这也把未来方向逼出来了。第一，参数和 harness 要能双向迁移：SKILL0 是技能→参数，反向则是把参数里难以调用的隐含能力显式化成技能/记忆。第二，要跨载体调度：记忆按交互写、技能按任务周期增长、协议/参数按项目或长期约束改，写入和回收的节奏不同，目前没有统一框架。

第三，作者把长程 agent 视为真正的试金石。静态 benchmark 测出厂能力，长程测运行中的净增益；第 k 步检索错，可能让第 k+1 步调错技能，后面整条链偏移；harness 操作不可微，训练/测试边界消失，错误还可能写回记忆形成正反馈。按附录 B 的表数，14 个代表 benchmark 里，8 个仍是参数载体、5 个只看 harness 的单一类、只有 SEAGym 同时覆盖三条轴（载体只覆盖参数和协议）；这个分布支持“评测缺口”的判断，但表格是代表性样本，不是穷举，数量不能当研究热度。论文还提出可验证奖励（verifiable rewards）是让系统自己持续改进的桥，但主要适用于代码、数学、单元测试这类可自动验证的任务；写作、咨询、长期规划仍缺信号。作者最后把“前沿模型（frontier model）的持续学习”排在领域特定持续学习之前——这是价值排序，不是综述数据推出来的定理；论文也没有给出统一的长程基准，长程评测仍是开放问题。

## 我能带走什么

一条判断规则：

> 以后看到一个“会学习”的 agent，我先不问它是不是又微调了模型，而问：**这次学到的东西写进了哪个载体？为什么是这一层？写入时怎样限制对旧能力的扰动？下次凭什么还能找到并使用它？**

这条规则可以直接用在两个地方。

**设计 agent 的记忆/技能/规则时**：先给能力按“通用性 × 过期速度 × 调用频率”分层。高频、跨任务、稳定的，往参数/技能固化；低频、情境绑定、易过期的，留在记忆/上下文，并设计主动遗忘和回收。不要把所有“学到的东西”都倒进一个向量库，也不要把所有“重要经验”都拿去微调。

**评估一个持续学习系统时**：不要只看单点任务分数。至少追问三件事：更新后旧能力还在不在（保留）、新能力能不能迁移到相邻任务（迁移）、错误会不会通过记忆/反馈回路被写回去并放大（漂移）。如果一篇工作只报了“在新任务上更高”，它可能只证明了“写进去了”，还没证明“持续学习成立”。

这篇综述最耐用的地方，可能不是三轴本身，而是它逼着你把“学习”从一个动词拆成三个问题：**什么时候写、写到哪里、怎么写才不弄坏旧的。** 一旦这样问，参数微调、记忆、技能、协议就不再是四个互不相干的赛道，而是同一个能力安置问题的不同答案。
